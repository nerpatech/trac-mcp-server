# Changelog

All notable changes to trac-mcp-server will be documented in this file.

Format based on [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Security
- **The link probe no longer sends the caller's Trac password to any host an authored link names (Trac #118).** `TracClient` sets `session.auth`, so `requests` attached `Authorization: Basic ...` to every request on the session, whatever its host. The write gate (#64), `convert_preview` and the render checks probe every InterTrac-dispatcher-shaped href, on any host, so a document containing `[http://attacker.example/intertrac/wiki%3AX x]` handed the caller's username and password to `attacker.example`. Callers scoped by #110's allowlist were protected; every unscoped caller on the LAN daemon was not
  - **Enforced at the session, not at each call site**: `core/scope.py`'s `ScopedSession.send()` sees the first request and every redirect hop `requests` follows. It removes `Authorization` from any request off the client's own origin (`requests`' own `should_strip_auth` rule: same hostname, scheme and port, plus the http -> https upgrade on default ports), and, for a client with an allowlist, refuses an out-of-scope request unsent with `DestinationOutOfScope`. Any other code that uses `client.session` is covered too, not only the probe
  - **A foreign target is still probed, anonymously** (the operator's choice, option 1(a)). A public Trac stays checked; a private one answers 401/403, which reports as unchecked, never as a broken link. On the cached corpus of 1,020 documents from both stores, the only foreign origin is `trac.edgewall.org` (210 hrefs), and all 210 still resolve anonymously
  - **`preview/targets._get` lost its hand-followed redirect loop**; scope helpers moved from `preview/targets.py` to `core/scope.py` (still importable from `targets`). Every session now follows at most 5 redirects, the bound the scoped loop had, so a redirect loop is an unchecked target rather than 30 requests
  - **One derivation, mapped everywhere**: the session and the probe's up-front pass share `core.scope.scope_for(config)`, and a refusal raised inside any tool is reported as `instance_not_allowed` by the tool dispatcher, not as `server_error`. An IDN `trac_url` keeps its credentials (its own origin is compared in prepared form), and a scoped client's http base also admits its https upgrade on the default ports, the one origin change the credential rule allows
  - **Tested on real sockets**: two `http.server` listeners stand in for the client's own Trac and a foreign host. On `master`, the foreign listener received `Basic` decoding to the test's `username:password`. Seeded mutants (no credential strip; no scope refusal) each fail their tests

### Added
- **`ticket_render_check` and `wiki_render_check` now return the de-duplicated ticket list in `structuredContent`, as `ticket_refs` (Trac /trac_mcp_server #152).** The `Ticket refs (N): ...` line from #151 is in the text block only, and Claude Code shows `structuredContent` in preference to the text, so the one list that exists to catch a mistyped `#N` that hits a real ticket never reached it
  - **New top-level `ticket_refs`**, after `sections` and before `stats`: a list of `{"ticket", "ref", "summary", "first_section"}`. `ticket` is the int (`null` only when no link to it had a `/ticket/N` href), `ref` the key the text line prints (`#N`, or the whitespace-collapsed link text when the href has no `/ticket/N`, uncapped), `summary` Trac's title without its leading `#N: ` or `Comment M for #N: ` (`null` only when no link to that ticket had a title), `first_section` the section the ticket was first seen in (`description`, `comment 3`, `page`), even when a later link supplied the summary. Complete and not shortened: the 50-entry and per-entry caps apply to the text line only, whose overflow tail now reads `(all in structuredContent ticket_refs)` instead of `links.ticket`. `links.ticket` is unchanged
  - **One helper for both**: `_ticket_refs` holds the de-duplication (missing links skipped, first-seen order, the first link's values win; a later link fills in a still-null `ticket` or `summary`, and a `#N: ` titled link replaces a summary that did not come from one) and `_ticket_refs_line` only formats its list, so the two cannot drift. `_section_name` is the bracketless form of `_section_label`, shared by `first_section` and the text block. `docs/reference/mcp-tools.md` documents the key
  - **Tested**: a ticket cited in the description and a comment gives one entry; `first_section` is the first section, including when only a later link has a `#N: ` title (the summary comes from the later one); a missing ticket is absent; a `comment:` link title is stripped; an untitled link and an href with no ticket number give `null` summary / `ticket`; no ticket links gives `[]`; `wiki_render_check` returns it; 60 tickets are all in the structured list while the text line stops at 50 and names `ticket_refs`; and the tickets the text line names equal the structured `ref`s in the same order over a fixture with a duplicate
  - **Seeded**: with `_document_response` building `ticket_refs` by its own pass that drops the `shaped` rule, `test_first_section_stays_first_when_a_later_link_has_the_summary` failed; with that pass returning the list reversed, it and `test_text_line_and_structured_list_share_one_helper` and `test_structured_list_is_complete_while_the_text_line_caps` failed; all passed again once restored
  - **Review fixes**: both tool descriptions said the ticket list was in the text result "for clients that only see text"; they now point at `structuredContent.ticket_refs` as well as the `Ticket refs` line. `_ticket_ref_key` returns `(key, number)`, so `_ticket_refs` no longer searches the href twice, and a fallback key is no longer cut at 80 characters (the text line still caps each entry). A later link now fills in a `ticket` that was `null` (a first link whose href had no `/ticket/N`, keyed by its text `#5`) and a `summary` that was `null` (including from a `Comment M for #N:` title). Tested: each fill-in, an over-80-character fallback `ref` returned whole while the text line entry is capped, and the descriptions. The shared-helper test now compares the text line with `_ticket_refs_line(structuredContent["ticket_refs"])` instead of parsing it. Seeded: with `_document_response` returning the structured list reversed, that test and the 60-ticket test failed; restored, all passed

- **A versioned wiki write can no longer silently replace a write that lands while it is in flight (Trac /trac_mcp_server #129).** Stock `wiki.putPage` ignores its `version` attribute, so `put_wiki_page` checked the version with a separate `wiki.getPageInfo` first (#120); a write by someone else between that read and `putPage` was overwritten, which #130 could only flag after the fact
  - **New plugin method `wiki.putPageIfVersion(pagename, content, attributes, expected_version)`** in `plugins/tracrpc_comment` (component `WikiConditionalPutRPC`, module `tracrpc_comment.wiki_put`; the egg goes to 1.1.0). It loads the page, compares its version and calls `WikiPage.save` inside one `env.db_transaction`; the `wiki` table's `(name, version)` primary key makes a write that commits between the comparison and the `INSERT` fail the `INSERT`, so the call refuses on every backend. An `IntegrityError` is reported as the conflict only if the re-read version differs from `expected_version` (another writer stored first); otherwise the original error propagates. A mismatch raises fault code **409** whose message starts `[wiki-version-conflict current_version=N]` (`none` for a missing page), and stores nothing. `expected_version` 0 means "create only if absent". Saving goes through `WikiPage.save` itself (validation, "Page not modified", change listeners); permissions are `WIKI_VIEW`, then `WIKI_MODIFY`/`WIKI_CREATE`/`WIKI_ADMIN` as for `putPage`, checked against the page's resource. The author is always the caller, and `readonly` changes only when passed
  - **`put_wiki_page` uses it for every versioned write** and maps the conflict fault to the existing `WikiPageConflict`, so `wiki_update`, `wiki_file_push` and `trac-mcp wiki-push` have no new error path and their responses are unchanged. A method-not-found fault (no plugin) falls back to the #120 precheck + `putPage`, unchanged, and is remembered per client for five minutes, so a plugin-less instance pays the extra round trip once per burst while a plugin deployed later is picked up without restarting the daemon. A `version` below 1 (0 or negative; versions start at 1) skips the plugin and is refused by the precheck, so `0` cannot create a page through the plugin path and a negative never reaches the plugin's "non-negative integer" fault, which `wiki_update` would read as a conflict. A create (`version=None`) keeps today's path. The #140 read-back and the #130 `possible_overwrite` check run on both paths. Any other fault from the plugin propagates without TracXMLRPC's `while executing 'wiki.putPageIfVersion()'` suffix, whose "version" `wiki_update` would otherwise read as a conflict
  - **Tested**: the plugin offline against real Trac: a matching version stores, a stale one raises the 409 and stores nothing, permission is refused without `WIKI_MODIFY` on that page (including a policy that denies one page only), and a **forced interleave** on a file-backed SQLite environment -- a second writer on its own thread commits right after the version is read -- is refused with the second write intact. The client with `_rpc_request` mocked: the plugin path is taken, the conflict becomes `WikiPageConflict`, a missing method falls back and the precheck still refuses a stale version, a create never calls the plugin; `wiki_update` and `wiki_file_push` run through the plugin path with a real client. Seeded: re-reading the page before the save (the old check-then-write shape) or dropping the `IntegrityError` mapping fails the interleave tests; dropping the conflict mapping, the fallback or the fault unwrapping fails their tests. Deploying the plugin and the live interleave test on `/trac_test` are left to the local session

- **`convert_preview` can now be told where the draft is going, so `attachment:` and `comment:` links are checked in context (Trac /trac_mcp_server #126).** The preview called `build_warnings` with no attachment list and no comment numbers, so a valid bare `[attachment:FILE label]` link to a file the target holds reported `missing_local_target` at `error`, while the write gate accepted the same text; `dangling_comment_ref` never ran in a preview at all
  - **Two optional, mutually exclusive arguments**: `page_name` (the wiki page the draft will be written to) and `ticket_id` (integer >= 1, the ticket whose description or comment it will become). Both together, a boolean or non-integer or sub-1 `ticket_id`, or an empty `page_name` is a `validation_error`. Neither given leaves the behaviour unchanged: no lookups, no new response line, and `target` is `null` in the structured result
  - **Reuses the gate's helpers**: `write_gate._attachment_names` and `_known_comment_numbers` are now public (`attachment_names`, `known_comment_numbers`). The attachment lookup runs only when the converted TracWiki contains `attachment:` and fails closed (a failed lookup, or a page that does not exist yet, keeps the links as errors); with `ticket_id`, the comment lookup runs only when it contains `comment:` and fails open (no changelog, no `dangling_comment_ref`). `page_name` never fetches a changelog
  - **Response**: a `Checked against: ticket 126` / `Checked against: wiki page Foo/Bar` line right after the summary line, with ` (N attachment(s))` when the attachment lookup returned a list, or ` (attachment list unavailable: bare attachment: links stay errors)` when it failed. The structured result gains `target`: `{"realm": "ticket"|"wiki", "id", "attachments_checked", "comments_checked"}`. `docs/reference/mcp-tools.md` gains the missing `convert_preview` section
  - **Tested**: against mock clients using the write gate's own fixture shapes (`<a class="missing attachment">`, a changelog of 5-tuples). A held file clears the finding for a ticket and for a page; no target, a file the target lacks and a failed lookup each keep it at `error`; no `attachment:`/`comment:` in the content means no lookup; the validation cases refuse. Seeded: with the `attachment_names=` pass-through to `build_warnings` removed, `test_ticket_target_clears_a_held_attachment` and `test_page_target_clears_a_held_attachment` fail; with `known_comment_numbers=` removed, `test_ticket_target_runs_dangling_comment_ref` fails
  - **Review fixes**: a failed comment lookup no longer reads as clean. `target.attachments_checked` and `target.comments_checked` are now tri-state (`null` = lookup not needed, `true` = ran and returned a set, `false` = ran and failed; `comments_checked` is always `null` for `page_name`), and the `Checked against:` line gains ` (comment list unavailable: comment: links not checked)` after any attachment clause when the comment lookup failed. Each argument's own shape is validated before the mutual-exclusion check, so `page_name: ""` with a `ticket_id` reports the empty name. Tested: a raising `get_ticket_changelog` says so and sets `comments_checked` false; unneeded lookups give `null`; seeded with the comment-unavailable clause removed, the new test fails

- **A disabled write gate now says so, on every gated write, in `list_instances` and `ping`, and in the startup log (Trac /trac_mcp_server #153).** `TRAC_WRITE_GATE=0`, left over from a test, sat in the shared daemon's env file and turned the link gate off for every project on the host, and nothing showed it: with the gate off, `gate_or_refuse` returned no lines at all, so a write it never checked looked exactly like a clean checked one. It came to light only when a broken bare ticket link went through
  - **Every gated write carries one line when the gate is off**: `NOTE: the write gate is OFF on this daemon (TRAC_WRITE_GATE=0, or write_gate: false in its config file), so this write was NOT link-checked -- not verified clean.` The write still succeeds; the switch does what it did (ticket #64 ruling 5). `gate_or_refuse` returns it, the same way a gate that could not run returns its `UNCHECKED` note, and all five callers (`ticket_write`, `ticket_comment`, `wiki_write`, `wiki_file`, `milestone`) already append the returned lines on every success path. The line is returned on every call, also for a write with no text, since it reports the daemon, not the content. It names the YAML key as well as the env var, because the switch can be set either way
  - **The batch tools say it too**, once per call rather than per item: they gate each item through `check_write` and never reached `gate_or_refuse`
  - **It is in `structuredContent` too, as `gate_notes`**, on the tools whose handler returns a dict (`wiki_file_push`, `ticket_batch_create`, `ticket_batch_update`): Claude Code shows `structuredContent` in preference to the text block, so a note carried only in the text was invisible there. `wiki_file_push`'s `gate_notes` also carries the gate-on advisory lines it appends to its text. A list, empty when there is nothing to say
  - **`list_instances` and `ping` report `write_gate: true|false`**, top-level in `structuredContent` and as a text line. `ping` now returns `message` (its full text) and `api_version` in `structuredContent` as well, for the same reason. `list_instances` reads it from the instance registry's default config, which every routed instance's config is copied from (ticket #117), so a caller whose allowlist leaves out the default instance, and so has no client, still gets it
  - **The startup log gains a `write_gate=on|off` line**, at `WARNING` when the gate is off, written once the lifespan has loaded the Trac config that carries the switch. The `file_access=..., max_inline_bytes=...` line stays where it was, straight after `set_file_access` and before the lifespan, so a failed lifespan validation still leaves it in the journal
  - **Tested**: with the gate off, every gated write path (`ticket_create`, `ticket_update` comment, description and field-only, `ticket_comment_edit`/`_reply`, `wiki_create`, `wiki_update`, `wiki_file_push`, `milestone_create`/`_update`) stores a broken link, carries the line and never renders. With it on, the line is absent. Both batch tools carry it once when off and not at all when on, and `wiki_file_push` and both batch tools carry it in `gate_notes` as well. `list_instances` and `ping` report both states, and the startup log line is tested at both levels and through `main()`, with `file_access` logged even when the lifespan fails. Seeded check: with the line removed from `gate_or_refuse` the twelve gate-off tests failed, and with it removed from the batch helper the two batch tests failed; removing each of the `gate_notes` keys (`wiki_file_push`, the batch tools) and `ping`'s `message`, `api_version` and `write_gate` keys failed the test written for it; all passed again once restored

- **`wiki_conventions`, a read-only tool for an instance's wiki style (Trac #123).** "How do I write a page on this instance?" took a `WikiStart` read, a hand-followed style link and a hunt for template pages; now it is one call with no arguments of its own (the usual optional `instance` routes it)
  - **Returns four things**: `style` (the label of the instance's declaration, or `undeclared` / `malformed`), `declaration_lines` (the marker lines found), `style_page` (the style page's body as stored with its version and the instance it was read from, or `null` when no style was parsed) and `templates` (every `PageTemplates/*` page, name and version and body as stored, sorted by name; the stock `PageTemplates` help page is not one)
  - **The declaration is a line of `WikiStart`, from column 0**: `'''Wiki style:''' [auto_pm:wiki:Rules/documentation/WikiStyleAgent agent]`, or `[wiki:... agent]` for a page on the same instance. Nothing is hardcoded, neither an instance nor a style name. A `{{{ }}}` block is blanked first, so a quoted line never counts. Any line starting `'''Wiki style:'''` (after whitespace) that fails the pattern, or valid lines that disagree, make the style `malformed`; identical duplicates are accepted; no line, or no `WikiStart`, is `undeclared`
  - **A style page on another instance is read within the caller's allowlist** (the InterTrac prefix is the instance's path, same host), through the same registry the dispatcher uses. A refusal never fails the call: `style_page` carries `available: false` and a `reason` (`instance_not_allowed`, `unknown_instance`, `not_found`, `permission_denied` or `error`) with the message, and the style and templates are still returned
  - **Tested**: the parser as a pure function (labels, same-instance and prefixed links, garbage, leading whitespace, missing label, disagreeing and duplicate lines, fenced lines, empty text) and the handler against a fake client and registry; a live test on `/trac_test` writes a probe template and a probe style page, appends a declaration to `WikiStart` and restores it. Seeded parser defects (fences not blanked, leading whitespace accepted) each fail their tests

- **A wiki update that may have overwritten someone else's write is now flagged (Trac /trac_mcp_server #130).** `put_wiki_page` refuses a stale `version` before calling `wiki.putPage` (#120), but a write that lands between that check and `putPage` is still replaced without anyone noticing: A checks version N, B stores N+1, A stores N+2, and A got a plain success. Since #140 the page is read back after the write, so the evidence was already there
  - **Detect only, no extra RPC** (preventing it is #129). When `version` was given and the read-back says anything other than `version + 1`, `put_wiki_page`'s result carries `possible_overwrite: True` and `intervening_versions` (`version + 1 .. new - 1`). Every result now carries `possible_overwrite`; a create (`version=None`) never sets it, and a failed read-back (`WikiPageStoredReadbackFailed`) is unchanged, since it says nothing about versions
  - **`wiki_update` and `wiki_file_push`** add a warning line naming the intervening versions and suggesting `wiki_diff(page_name=..., from_version=N, to_version=...)` to inspect them. The result stays a success: the page was stored. `wiki_file_push`'s structured result carries `possible_overwrite` next to `readback_failed` (plus `intervening_versions` when true); both are documented in `docs/reference/mcp-tools.md`
  - **`trac-mcp wiki-push`** prints `trac-mcp: warning: possible overwrite ...` on stderr and still exits **0**: the write succeeded, and a non-zero code would read as "not stored" and invite a retry that writes the page again
  - **Caveat**: a write that lands just *after* this one, before the read-back, also raises the flag, and the read-back then reports that later version (the reported `version` was already that later one before this change). Hence "possible", and a warning rather than an error
  - **Tested**: a real `TracClient` with `_rpc_request` mocked. An update sent with version 3 that reads back 5 is flagged with intervening version 4 in the client result, and warns in `wiki_update` and `wiki_file_push`. One that reads back 4, and a create, stay quiet. Each flag/warning test failed with the fix removed (on `master`, and against seeded mutants of the client check, each tool's warning, the push's structured flag and the CLI's stderr line); the quiet-path tests failed against a client that flags every update. The live check that an uncontended write stays quiet on the test instance is left to the local session
  - **Review fixes**: a float `version` such as 3.0 (a JSON-schema "integer") no longer raises `TypeError` after the page is stored, and the warning says that if the diff is exactly this write's own change, nothing was dropped

- **A Markdown list item that continues after its nested list now draws an advisory (Trac #125).** Trac cannot continue a list item once a nested list has started: it ends the list, renders the next block outside it (a paragraph as a blockquote, a fenced code block as a `<pre>`) and starts a new list for the following item. Since #112 the converter keeps an item's children in source order, so `- Cause: unknown. Suspects:` + a nested list + an indented paragraph + `- Guard: next item.` converts faithfully and then renders split, with nothing to tell the author (measured live on `/trac_test`)
  - **New code `list_item_split`, severity `warning`** (never `error`, so the write gate does not block it; listed in `ADVISORY_CODES`). The content survives and only the list structure splits, so refusing would be wrong; the message names the item, the block that follows the nested list, and the remedy (move the block out of the list in the source, or accept the split). Detection is `find_list_item_splits`/`describe_list_item_split` in `converters/markdown_to_tracwiki.py`, parsing with the converter's own mistune AST so the two agree on what is a list and what sits inside a fence. Nested items count (`depth` 1 for an item of a nested list), and one finding is recorded per item
  - **Where it runs**: `convert_preview` with `format` markdown, and `wiki_file_push` on a Markdown push, where it is appended to the response's `warnings` ("Conversion warnings:") and never refuses the push. TracWiki-declared writes skip it, as they skip the other Markdown-source checks
  - **Recall sweep**: both stores refreshed 2026-11-03, 2012 documents (wiki pages, ticket descriptions and comments; the stock `TracLinks` page is excluded from both stores because it faults on render). Each stored TracWiki source was run through `tracwiki_to_markdown` and then the detector: **0 documents raise it**, so there is no existing population to be noisy for. A seeded check shows the sweep can see the shape: the converter's TracWiki output for the ticket's input, read back through `tracwiki_to_markdown`, does raise it. Reading the raw stored sources as if they were Markdown gives 2 hits, both the ticket's own example quoted inside a TracWiki `{{{ }}}` block (#112, #125), unreachable because TracWiki-declared writes skip the Markdown checks
  - **Tested**: the ticket's input yields exactly one finding (item, block `paragraph`, depth 0) and one `warning` through `build_warnings`; silent controls for a sub-list with nothing after it and for the same input inside a fenced block; a fenced code block after the sub-list, an ordered parent and a depth-1 split are reported; item text holding a code span or `[[...]]` is reported restored with no NUL byte; the gate does not block it; `wiki_file_push` stores the page and carries the message. The seeded tests failed against a detector stubbed to return nothing before the real one was written

- `ticket_check_list`: checks a whole list of ticket numbers, or texts in summary/description/keywords, against Trac in one call and returns which exist (with the requested fields) and which are missing, instead of one `ticket_search`/`ticket_get` call per value. Values are comma or new line separated, or a JSON array; texts match as whole words; an optional query restricts where to look (Trac #139, PR 116)
  - **Review fixes (Trac #139)**: the caller's `query` is refused if it could override the chunk query (`max`, `page`, `order`, `desc`, `group`, `groupdesc`, `col`, `format`, `report`, `verbose`, `rows`, `row`, an `or` clause, a clause without `=`, or the chunk's own field); `match_field` must be a plain field name. Text values are escaped, not blanked: the Trac query searches the longest segment of a term (split on whitespace, `\` and `"`, leading `-` stripped) with `|` and `&` escaped, and the whole-word filter still decides on the full term; a term with nothing to search is listed in `unsearchable`. One failed `get_ticket` no longer fails the call: its id is in `failed_ids`. Unset fields are `""`, not null; a requested `id` field keeps the real id; `²`, `##5` and `#` are `not_a_ticket_number`; `values="[]"` is an empty-values error; each hit carries its `url`
  - **Review fixes, round 2 (Trac #139)**: `match_field` is checked against the instance's real fields (`get_ticket_fields`, text mode only) and must be the exact name of a `text` or `textarea` field, else a `validation_error` lists the allowed ones; the shape check is `fullmatch`, so `"summary\n"` no longer passes. The query needle depends on the field: a list field (`type` text, `format` list: `keywords`, `cc`) keeps the longest word, any other field searches the whole value (`disk quota exceeded`), split only at a backslash; the literal `$USER`, which Trac replaces with the caller's name, separates segments in both. Each ticket is fetched once per call and a failure is not retried. In text mode a value with no match while a candidate of its batch failed to load is listed in `unresolved`, not `missing`. In id mode a ticket that exists but failed to load stays in `found` with `id` and `url` only (and in `failed_ids`), so `found_count` no longer depends on `only_missing`. A value of more than 18 digits is `not_a_ticket_number` instead of reaching `int()`. `url` cannot be requested as a field (as for `id`). Docs: `only_missing` in text mode still fetches every candidate; SQLite folds case for ASCII only, so a non-ASCII case difference can be reported missing
- OIDC per-user auth for the http transport, for shared/multi-tenant deployments (e.g. one `trac-mcp-server` serving many users through a gateway like LibreChat, each with their own Keycloak/OIDC identity) where a single static bearer token would misattribute every action to one shared identity
  - New `TRAC_MCP_OIDC_RPC_URL` / `server.oidc_rpc_url` setting: when configured, every request must carry the caller's own OIDC access token in the standard `Authorization: Bearer <token>` header, forwarded verbatim to that URL (typically an Apache + `mod_auth_openidc`-protected Trac endpoint, validating the token and mapping it to a Trac username) -- the standard header, not a custom one, matches how an MCP client's own OAuth flow per server (e.g. LibreChat's `oauth:` config) actually attaches a token
  - No fallback to a shared service-account identity, by design: a request missing a bearer token gets `401` at the transport layer (new `OidcTokenRequiredMiddleware`) before it ever reaches tool dispatch, and `TRAC_USERNAME`/`TRAC_PASSWORD` are not required in this mode -- `Config.oidc_only` relaxes that requirement and skips the startup connectivity self-test (there's no shared credential to test with) unless real credentials are configured anyway
  - Mutually exclusive with the existing static `TRAC_MCP_AUTH_TOKEN` gate -- both are read off the same `Authorization` header for different purposes, so `validate_server_config()` now rejects configuring both at once; `oidc_rpc_url` alone satisfies the existing non-loopback-bind safety check
  - `instance` argument (multi-instance addressing) is rejected with a clear error in this mode rather than silently ignored -- OIDC per-user auth serves only its single configured endpoint
  - Per-token `TracClient` cache (`mcp/oidc.py`: `OidcClientCache`), bounded to 256 most-recently-used tokens with FIFO eviction, so a session's calls reuse one connection pool instead of paying for a fresh one per call
  - New `src/trac_mcp_server/mcp/oidc.py` (`OidcClientCache`, `extract_bearer_token`); `TracClient`/`Config` gained `bearer_token`/`rpc_url_override`/`oidc_only` for the Bearer-vs-Basic-auth and RPC-URL-override split this required
  - `TRAC_MCP_OIDC_RPC_URL` is checked at startup: it must be an http(s) URL with a host, and plain `http` on a non-loopback host needs `TRAC_MCP_OIDC_ALLOW_INSECURE_HTTP=true`, since every request forwards a user's token to it. It is refused outside the http transport
  - `list_instances` reports only the configured endpoint in this mode and makes no outbound call: its project discovery would authenticate as the shared account
  - The middleware and dispatch read the same one of several `Authorization` headers, the first; an evicted client's pooled connections are closed (`TracClient.close()`)
  - `ticket_update` finds a new comment's number in this mode: the lookup filtered by a username the client does not have, so every comment got a warning instead

- **Native multi-identity support in the shared HTTP transport (Trac #102).** A `TRAC_IDENTITIES` file maps several distinct bearer tokens to their own Trac username/password, so one shared daemon can serve several operators under their own Trac identities -- replacing today's one-process-per-identity deployment. `BearerAuthMiddleware` now checks a request's token against *every* configured token (the static one and every identity's), stashing a match on `scope["trac_identity"]`; `mcp/server.py`'s two dispatch sites (`handle_call_tool`, `handle_read_resource`) read it back via `_caller_identity()` and pass it into `InstanceRegistry.resolve()`/`get_client()`

- `tracwiki_to_markdown` no longer corrupts `[[Page]]` WikiLinks read via `wiki_get`/`wiki_search` (Trac #28, critical): plain double-bracket links were being routed through the unknown-macro placeholder mechanism, which silently discarded single links and, when two or more placeholders landed near each other, merged them into one unterminated construct with a leaked raw `\x00` byte
  - `[[Page]]` / `[[Page|Label]]` are now recognized as WikiLinks (matching Trac's own macro-name-registry-first resolution) and convert to real `[text](wiki:Page)` Markdown links; only a small allowlist of genuine Trac macro names, or any `[[Name(args)]]` carrying explicit arguments, still go through the macro path
  - Fixed two latent greedy-regex bugs this exposed: the macro-placeholder restore pass and the single-bracket `[url text]` link pass could each span past their own closing token into a neighboring link/macro when several appeared close together

### Added
- **A warning suite rule for damage that is invisible: `code_block_indentation_loss` (Trac #68).** Every other rule catches something a reader can *see* is wrong — literal markup, a dead link, a reference stuck in a code span. Feeding a TracWiki `{{{ }}}` block to the Markdown converter strips the leading whitespace from its body (the block is not recognised as a code construct, so ordinary paragraph handling eats it), storing syntactically invalid code with an **empty** warning list under a render that looks entirely plausible. It is visible only in the stored bytes, and it was committed twice inside #62 — a ticket whose subject was that exact corruption — caught both times only by reading the source back by hand
  - **`tracwiki_markup_in_markdown` could not have been widened to cover it.** That rule runs `blank_code_fences` first, which blanks a `{{{ ... }}}` region *including its delimiters*, so the `{{{` it scans for is erased before the scan reaches it. The shape that gets destroyed is precisely the shape it is built to ignore; #65's narrowing and this check are complements, not overlapping
  - **Detection lives in `converters/common.py`, not in the preview module**, so all three surfaces that still convert can reach it — `preview` is not packaged into the `trac-convert` binary, and #68 comment 4 measured `wiki_file_push` storing damaged bytes without ever calling `build_warnings`
  - **`wiki_file_push` refuses rather than warns.** An `error`-severity finding on a path that then stores the damaged bytes anyway would leave the corruption in the page and the recovery to whoever reads the response. `format="tracwiki"` still pushes the same file verbatim — the check gates on the declared format, not on the content. This is the one remaining write path that converts; #69 left it converting because it has a *filename* to go on
  - `convert_preview` reports it as a structured warning at severity `error` (the precedent is #59, where `intertrac_target_captured_punctuation` became an error for naming a genuinely dead link), gated off for TracWiki-declared input, where nothing converts and nothing can be lost. `trac-convert` reports it on stderr and still writes its output: that binary stores nothing, so the caller still holds the input
  - **Deliberately narrow, and measured that way.** Blocks are paired by their stripped body content rather than by position (a positional rule skips any document whose block counts differ, e.g. one holding both an indented-Markdown block and a damaged `{{{` one — a false negative on a real defect), and indentation is compared *relative* to each block's own minimum (mistune legitimately dedents a fenced block nested in a list item, which absolute comparison called loss). Two accepted residuals: a uniform dedent of a whole block, and two identical damaged blocks, both stay silent. Zero new warnings across all 72 preview fixture rows, the store corpus, and every Markdown file in the repo
- Streamable HTTP transport (Trac #26): `trac-mcp-server --transport http` serves MCP over `POST/GET/DELETE <path>` (default `/mcp`) via a Starlette app run by `uvicorn`, alongside the unchanged stdio default
  - Stateful sessions (`Mcp-Session-Id`, the MCP SDK default), so one long-lived process can serve multiple concurrent clients/sessions
  - Optional static bearer token auth (`TRAC_MCP_AUTH_TOKEN` / `server.auth_token`), checked with `secrets.compare_digest`; unauthenticated requests get `401` + `WWW-Authenticate: Bearer`
  - Bind-safety guard: refuses to bind a non-loopback host for `--transport http` unless a token is configured or `--allow-unauthenticated` is explicitly passed
  - DNS-rebinding protection via the MCP SDK's `TransportSecuritySettings` (`Host`/`Origin` allow-listing, extensible via `server.allowed_hosts`/`allowed_origins`)
  - Unauthenticated `GET /healthz` for container liveness/readiness probes
  - New `--transport`, `--host`, `--port`, `--path`, `--allow-unauthenticated` CLI flags and `TRAC_MCP_TRANSPORT`/`TRAC_MCP_HOST`/`TRAC_MCP_PORT`/`TRAC_MCP_PATH`/`TRAC_MCP_AUTH_TOKEN` env vars, plus a new `server:` YAML config section — no `--auth-token` CLI flag by design (would leak into the process list)
  - New `src/trac_mcp_server/mcp/http_app.py`: `BearerAuthMiddleware`, `build_http_app()`, `run_http()`
  - `Server("trac-mcp-server", version=__version__)` now reports the project version over HTTP too (previously only the stdio path set this, so `StreamableHTTPSessionManager`'s auto-generated init options would have reported the `mcp` SDK version)
  - New docs: [HTTP Transport Reference](docs/reference/http-transport.md); updated README, CLI, configuration, and deployment docs
- Multi-instance Trac support (Trac #18): every MCP tool and the `trac://wiki/*` resource now accept an optional `instance` argument that routes the call to another Trac project instead of the default one, with no server restart required
  - Named instances declared via a new `instances:` section in config files, or an out-of-band `TRAC_INSTANCES` file (YAML/JSON), with live reload on edit
  - Ad-hoc addressing (`instance: "/project-path"`) reaches any project on the same Trac host as the default instance using the default's credentials, restricted to the default instance's exact scheme+host so credentials can never be sent to another host
  - New `list_instances` tool (28th documented tool, 43rd registered including `ping`) surfaces configured instances plus, via a new `scrape_project_index()` web-scraping helper, other projects discoverable on the host's "Available Projects" index
  - `src/trac_mcp_server/instances.py`: `InstanceSpec`, `InstanceRegistry` (resolve/get_client/describe, with per-URL client caching and mtime-gated live reload), `UnknownInstanceError`, `load_declared_instances()`
